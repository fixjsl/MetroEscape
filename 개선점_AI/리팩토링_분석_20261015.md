# MetroEscape 리팩토링 대상 분석

- 분석 기준 커밋: `78ea472`
- 범위: `Assets/Script` 아래 직접 작성한 C# 127개 파일(약 9,000줄)과 저장소 구조
  - 상태머신·전투, 매니저·시스템·아이템, UI·저장소 구조의 3개 영역으로 나눠 전체를 읽음
- 줄 번호는 위 커밋 기준이라 코드를 수정하면 달라질 수 있음
- 표시: 🔴 높음 / 🟠 구조 / 🟡 중간 / 🟢 낮음

## 1. 🟠 구조(아키텍처)

### 1-1. 상태머신 공통 기반이 없음
- 리플렉션으로 상태를 초기화하는 코드가 Player, Monster, Boss에 3번 중복됨: `PlayerStateMachine.cs:163-175`, `MonsterStateMachine.cs:53-65`, `BossStateMachine.cs:91-105`
- 몬스터마다 `Assembly.GetTypes()`를 다시 호출함. 필터 기준도 서로 다름(namespace 문자열 vs `IsSubclassOf`)
- 제안: 제네릭 `StateMachine<TState>`를 만들고 타입 목록을 static으로 캐싱. `ChangeState`, `Statecaches`, `canChanged` 리셋을 이 기반 클래스로 통합(B4도 해결)

### 1-2. Monster와 Boss 상태 클래스가 거의 복사본
| Monster | Boss | 차이 |
|---|---|---|
| `Hit` | `BossHit` | Boss만 `PreserveBattleTimer=true` |
| `Battle` | `BossBattle` | Special 분기, 타이머 보존, 속도 필드 |
| `Chase` | `BossChase` | 전환 대상만 다름. `CheckDirection`/`OnTurnAnimationFinished`는 글자 그대로 같음 |
| `Return` | `BossReturn` | Boss 쪽이 더 정확함(null 체크, rotation 보정) |
| `Stun` | `BossStun` | animator.speed 처리. `BossStun.HandleDamage`는 base와 같음 |
| `Die` | `BossDie` | `AddKill`, `applyRootMotion` |
| `Attack` | `BossAttack` | 돌진 impulse `20f`가 양쪽에 하드코딩됨 |

- 제안: Boss 상태가 Monster 상태를 상속하고, 다른 부분만 virtual 메서드로 덮어씀(전환 대상, 타이머 보존 등)
- 회전 로직(6곳 이상)은 `FaceTowardX()`/`NeedsTurn()`으로 추출
- `OnHit` 중복은 hook 메서드로 통합

### 1-3. `PlayerStateMachine`(629줄)에 기능이 몰려 있음
- 한 클래스가 맡은 일: 입력 람다 12개, 입력 버퍼, 콤보/캔슬 윈도우, 처형 대상 탐색(OverlapSphere), 상호작용 대상 관리(LINQ), 무기 장착·IK, 라이트·SFX, 에디터 디버그
- 제안: `PlayerInputHandler` / `PlayerCombat` / `PlayerInteractor` / `PlayerEquipment`로 분리
- `CheckStateChange`(`:305-341`)의 전환 규칙이 `is Crunch`, `is Parry` 같은 타입 검사로 하드코딩돼 있음 → 각 상태의 `CanEnter`/`TryTransition`으로 옮겨 OCP 확보
- 상태끼리 머신의 public 플래그(`IsReturningFromAttack`, `PreserveBattleTimer`)로 값을 주고받음 → 진입 파라미터로 넘기는 방식으로 변경

### 1-4. `GameManager`도 여러 일을 함께 맡음
- 설정 저장, 디스플레이·품질, 오디오, 게임 시계와 이벤트가 한 클래스에 있음
- 제안: `SettingsService` / `AudioService` / `GameClock`으로 분리
- `TutorialStart()`는 실제로 "시계 시작"이라 이름 변경 필요
- 이벤트 `ChangeDay`의 주석과 실제 인자 순서가 다름
- `audioMixer` null 체크가 없음

### 1-5. 싱글턴 19개가 4가지 방식으로 제각각
| 방식 | 파일 |
|---|---|
| keep-first + DDOL + `Destroy(gameObject)` | GameManager, MetaProgressManager |
| keep-first, DDOL 없음 | GameStartFlow, MonsterManager, TutorialManager |
| last-wins(중복 방어 없음) | CycleManager, ItemPlacementController, ScreenPointLightManager, UI 대부분 |
| static 데이터 | ItemManager (`static Dictionary itemDB`) |

- `OnDestroy`에서 `Instance`를 정리하지 않음
- `MetaProgressManager`는 StartMenu 씬에만 있어서 다른 씬을 직접 실행하면 null이 됨. 그래서 `?.`가 곳곳에 있음
- 결합도: `PlayerStateMachine.Instance` 58곳(27개 파일), `GameManager.Instance` 53곳(13개 파일)
- 제안: `SingletonBehaviour<T>`(persistent 플래그 포함) + Bootstrap 씬 또는 `RuntimeInitializeOnLoadMethod`

### 1-6. 의존 방향이 거꾸로임
- 월드 오브젝트가 UI 싱글턴을 직접 호출함: `Campfire`, `ContainerObject`, `CraftingTable`, `BaseDepartureGate`
- UI끼리도 서로 호출함: PauseMenuUI → Crafting/Container/Inventory, ContainerUI → InventoryUI
- 반대로 UI가 게임 로직을 들고 있음:
  - `ContainerUI.TakeItem/UseFromContainer`(:57-83)가 컨테이너 리스트를 직접 수정
  - `CampfireUI`(:59-85)가 점화·요리 가능 규칙을 다시 계산
  - `CraftingUI`(:97-98)에 레시피 필터 규칙이 있고, 인벤토리 변경 이벤트를 구독하지 않음
  - `QuickSlotUI`가 숫자키 입력을 직접 처리해서 키 바인딩을 우회함
  - `GameOverUI`가 메타 진행 평가 시점을 결정함
- 제안: 로직은 모델(`ContainerObject`, `Campfire`)로 옮기고 `OnChanged` 이벤트를 둠. UI는 이벤트를 받아 표시만 함

### 1-7. UI를 한곳에서 관리하지 않음 (B9, B10의 근본 원인)
- `Time.timeScale`을 바꾸는 곳 5곳: PauseMenu, GameOver, GameClear, GameStartFlow, TutorialManager
- 커서 처리 3곳(`CursorLockMode.Locked`로 되돌리는 코드는 없음), 전투 입력 토글 7곳
- 제안: `UIPanel` 기반 클래스(Open/Close, BlocksInput, PausesTime, CloseOnCancel) + `UIStackManager`(Push/Pop, 참조 카운트, ESC 처리 한곳)

### 1-8. 저장/로드가 깨지기 쉬움
- 위치: `GameManager.cs:66,72`, `MetaProgressManager.cs:38,41`
- 빠진 것: try/catch, 원자적 쓰기, 스키마 버전
- `ResetProgress` 후 저장하지 않음
- `Editor/MetaProgressEditor.cs`가 직렬화 포맷을 따로 다시 구현함
- 제안: `JsonFileStore<T>`(load-or-default, temp 파일에 쓰고 rename, version 필드)

## 2. 🟡 데이터·도메인, 성능

### 데이터·도메인
- **소모품 클래스 중복:** `Food`, `Water`, `HealItem`, `DirtyWater`는 같은 로직
  - 타입(int/float)과 이름 규칙이 제각각이고, `CreateAssetMenu(fileName="HealItem")`가 복사돼 있음
  - `ConsumableItem` + `List<StatDelta>`로 통합
- **`ItemBase` 역할 과다:** 구체 클래스인데 크래프팅 레시피까지 들고 있음
  - `RecipeSO`로 분리
  - `ICreatable`과 `Weapon.Craft`는 dead code
- **`ItemManager`:** 씬마다 static Dictionary를 채움
  - `ItemDatabase` ScriptableObject로 바꾸고 `OnValidate`에서 중복·0 코드 검사
  - `MetaProgressManager.allPerks`는 `PerkDatabase`로
  - `LootTable`의 static 고유 드랍 집합은 런 상태 객체로 이동
- **`PlayerStatus` setter에 게임 규칙이 들어 있음:**
  - Hungry가 최대 무게를, Water가 최대 스태미나를 바꿈
  - Stamina가 0이면 이벤트가 반복 발생
  - 스태미나 회복 코드가 `Idle`/`Move`/`Crunch` 3곳에 중복됨
- **이동 상태 중복:** `Move`와 `Crunch`가 70% 이상 같음 → `GroundMoveState` 기반 클래스로 추출
- **PassiveState 실행 방식이 섞여 있음:** 코루틴 방식과 `LogicUpdate` 방식
  - `HungerThirst`는 `base.Enter()`를 부르지 않고 `OnTick`이 비어 있음
  - `Die.RespawnRoutine`이 상태 안에서 게임 흐름(CycleManager)을 제어함
- **상호작용 오브젝트 계층(`ItObjectBase`):**
  - `isInteracting=false`를 13곳에서 직접 해제함
  - `isStuck`은 쓰이지 않음
  - 열쇠 확인 로직이 중복됨(`Blockade`/`BaseReturnExit`), 퇴장 시 UI를 닫는 로직이 3곳에 중복됨
  - 상호작용 안내 문구 형식이 제각각이고, `ItemPickup`은 `"[F]"`를 하드코딩해 키 변경이 반영되지 않음
- **손전등 데이터 전달:** 셰이더 글로벌 변수에 문자열로 쓰고, 몬스터마다 매 프레임 문자열로 읽음
  - `MonsterUI`에는 같은 코드가 복사돼 있음
  - `static class ShaderIds`와 C# 상태 객체로 변경
- **사이클 리셋:** `CycleManager.cs:95,106`의 `FindObjectsByType` 대신 `OnCycleReset` 이벤트나 레지스트리 사용
- **튜토리얼:**
  - `TutorialManager`의 단일 `pendingTrigger` 슬롯 때문에 트리거가 유실됨
  - 50ms 폴링으로 할당이 발생함
  - `GameStartFlow`와 런 시작 로직이 중복됨

### 성능
- **`MonsterStateMachine.Detect`:** 0.1초마다 `OverlapBox`(할당 발생)와 `GetComponent` 호출, Linecast 2회, Distance 3회 → `NonAlloc`으로 바꾸고 캐시
- **`MonsterWeapon`:** `OnTriggerStay`에서 `GetComponentInParent`를 부르고, `FixedUpdate`에서 폴링하고, `Debug.Log`가 많음
- **상호작용 대상 getter:** 접근할 때마다 LINQ `OrderBy` 실행
- **UI 목록 갱신:** Inventory/Container/Crafting/PerkSelect/ZoneSelect가 새로 그릴 때마다 Destroy/Instantiate → 풀링
- **반복 호출:** `Camera.main`(MonsterUI, PlayerDialogueUI, Flashlight, ItObjectBase), `GameObject.Find("UICamera")`(MonsterUI:40)
- **매 프레임 할당:** `FlashlightRendererFeature.cs:89`의 `new ProfilingSampler`, `PerfLogger.OnGUI`의 `new GUIStyle`
- **`Inventory`:**
  - 아이템을 하나 지울 때마다 이벤트가 발생해 N+1번이 됨
  - 무게(float) 누적 오차
  - `slots`가 수정 가능한 public Dictionary

## 3. 🟢 코드 품질

- **Animator 해시:** 인스턴스 필드 → `static class PlayerAnim/MonsterAnim`
  - 레이어 번호 `0`/`1`은 상수로
  - Monster의 `sprint` 필드가 실제로는 `"chase"` 해시임
- **매직 넘버:**
  - 감지 게이지 `100/50/0.1/20`, 돌진 impulse `20f`(2곳)
  - 회피 속도 `60f`(이미 있는 `dodgeSpeed` 필드를 안 씀)
  - 시계 `2.5f`, 모닥불 `60f`, 퀵슬롯 `2`(3곳)
  - `Random.Range(3,5)`(int 오버로드라 3 또는 4만 나옴)
- **캡슐화:**
  - public 필드가 많고 `[SerializeField] public`처럼 중복된 경우도 있음
  - `OnEnable`/`OnDisable`이 public이고 `Die`에서 직접 호출함
  - `State.isBlock`이 public field
- **이름 정리:**
  - 파일·클래스: `hit.cs`, `Crunch`→`Crouch`(일괄 변경), `Doorcs`, `YeildCache`, `Layercache`, `DIYwaterfilter`, `ItObjectBase`, `NoiseABright`, `TimeManager`(실제로는 타이머)
  - 식별자: `staminaRecoverey`, `parrysucess`, `fillteringTime`, `OnAttackColider`, `onSelescted`, snake_case 혼용
- **namespace:** Player 상태(`Idle`/`Move`/`Hit` 등)가 global namespace에 있어 Monster 상태와 이름이 충돌함 → `PlayerStates` namespace 도입
- **인코딩 깨짐:** Monster 관련 주석과 `[Header("���")]`가 깨져 있고, 이 헤더는 인스펙터에 그대로 보임. `MonsterManager.cs`도 마찬가지
- **사용하지 않는 코드:**
  - `MonsterManager.cs` 전체, `IState`(구현체가 하나뿐), `ICreatable`, `Weapon.Craft`
  - `Return.EndReturn`, `Inventory.DropItem`(`RemoveItem`의 별칭일 뿐)
  - 쓰이지 않는 필드: `parryCost`, `dodgeSpeed`, `instantDetectRange`, `knockbackForce`, `holdPosition`, `NoiseABright.light`, `CameraFollow.lookAtTarget`
  - 쓰이지 않는 using(`System.Security`, `Unity.VisualScripting` 등)
- **남아 있는 디버그 로그:** `GameClearUI:24`, `InventoryUI:39,46`, `WeaponPickup:18`, `MonsterWeapon`
- **하드코딩 문자열:**
  - 씬 이름 `"MainMenu"`: 실제 씬은 `StartMenuScene`이라 확인 필요
  - Input action 이름이 7개 파일에 문자열로 들어 있음
  - 한글 UI 문자열 → 로컬라이즈 테이블이나 SO로
- **에디터 스크립트:**
  - `Assets/Editor`와 `Assets/Script/Editor` 두 폴더로 나뉘어 있음
  - `BakeMeshExporter`는 MonoBehaviour인데 Editor 폴더에 있음
  - scale curve 제거 루프가 3번 중복됨
  - `BossDebugEditor`가 매번 `Repaint`를 호출함

## 4. 저장소·프로젝트 구조

| 우선 | 항목 |

## 부록 A. B3 상세: 시간제 효과 시스템

### 재현
현재 데이터:
- `에너지드링크.asset`: 120초 동안 배고픔 감소 ×0.5, 수분 감소 ×0.5, 스태미나 회복 ×1.5
- `껌.asset`: 60초 동안 배고픔 감소 ×0.7

에너지드링크를 먹고 120초 안에 껌을 씹으면:
1. `OnUse`가 에너지드링크 코루틴을 `StopCoroutine`으로 중단함. 원래 값으로 되돌리는 코드는 `yield` 뒤에 있어서 실행되지 않음
2. 껌은 배고픔만 바꾸고 60초 뒤 배고픔만 원래대로 되돌림
3. **수분 감소 ×0.5와 스태미나 회복 ×1.5가 계속 남음**

또 되돌리는 방식이 "base 값으로 덮어쓰기"라서, 같은 스탯을 바꾸는 다른 효과(퍽 등)까지 지워짐.

### 설계 방향 (논의 결과)
- **스탯을 직접 덮어쓰지 않고 modifier를 등록했다가 해제하는 방식**으로 변경
  - `StatType` enum: 어느 스탯인지 나타내는 이름표. 새 *스탯*이 생길 때만 늘어남
  - `StatModifier` (class): stat, multiplier, source. class로 만들어야 참조 비교로 정확히 자기 것만 제거할 수 있음
  - `PlayerStatus`: `AddModifier` / `RemoveModifier` / `ClearModifiers` / `GetMultiplier`
- **계산 규칙:** 가장 센 버프 하나 × 가장 센 디버프 하나
  ```csharp
  float up = 1f, down = 1f;
  foreach (var m in modifiers)
  {
      if (m.stat != type) continue;
      if (m.multiplier > 1f) up   = Mathf.Max(up,   m.multiplier);
      else                   down = Mathf.Min(down, m.multiplier);
  }
  return up * down;
  ```
  스탯이 "작을수록 좋은지"와 관계없이 결과가 같으므로, 계산할 때 방향 정보는 필요 없음(UI에서 버프/디버프를 표시할 때만 필요)
- **직렬화 호환:** 기존 필드 `staminaRecoverey`, `hungerDecreasePerMinute`, `waterDecreasePerMinute`는 **필드로 유지**해서 기본값 역할을 맡김
  - 프리팹(`Prefeb/Idle.prefab:934-939`)과 씬 오버라이드(`Base&Main1`, `TutorialScene`)에 값이 저장돼 있기 때문
  - 계산값은 새 이름의 프로퍼티(`StaminaRecoveryRate` 등, `=>` 사용)로 만들고, 값을 읽는 5곳을 교체
- **효과 구조:**
  - `TimedEffect`(abstract, `[Serializable]`, `[SerializeReference]` 리스트로 아이템에 저장): `OnStart` / `OnTick` / `OnEnd` / `OnReapply`
  - 하위 클래스: `StatMultiplierEffect`(중복 시 지속시간 초기화), `HealOverTimeEffect`(중복 시 지속시간 연장, `OnReapply` override)
  - `ActiveEffect`: def, remaining, state. 실행 중 상태는 에셋에 공유되는 정의가 아니라 여기에 저장
  - `PlayerEffects`: `Apply` / `Tick` / `ClearAll`. 코루틴 대신 `Update`에서 남은 시간을 관리하고, 사망 시 `ClearAll`
- **주의:**
  - `Tick`에서 리스트를 도는 중에 바로 Remove하지 말 것(역순 for문 사용)
  - `TimedEffectItem` 필드를 바꾸면 에셋에 입력한 값이 초기화되므로 작업 전에 커밋하고 기존 값을 메모
