# 구현 현황 점검 (2026-09-27)

논문 1~3장과 4장 초고의 서술을 `E:\Popol\SubwayExit`의 실제 코드·씬·에셋과 대조하였다. 2026-09-19 점검 이후 달라진 것과, 4.3.1 확장성 검증에 쓸 재료를 정리한다.

---

## 1. 4.3.1 확장성 검증에 쓸 사례

### 사례 1 — 구역 확장 (주 사례)

`확장성 검증 깃 스샷/구역확장 코드 일반화 2구역.png`가 정량 근거다.

```
git diff main...feature/zoneExpension --numstat -- "*.cs"
48  13   Assets/Script/Manager/CycleManager.cs
12   0   Assets/Script/Manager/ZoneEntry.cs
14  10   Assets/Script/Object/BaseDepartureGate.cs
58   0   Assets/Script/UI/ZoneSelectUI.cs
```

신규 2파일 70줄, 기존 2파일 62줄 수정.

**주장을 한 단계 낮춰야 한다.** 논문 1.2.2와 3.6은 "새로운 구역을 기존 코드의 수정 없이 추가"라고 쓰고 있으나, 위 디프는 기존 파일 두 개가 실제로 수정되었음을 보인다. 이 스샷을 근거로 제시하면 그대로 반증 자료가 된다.

정확한 서술은 **일회성 일반화**다. 1구역에서 2구역으로 갈 때 든 비용은 구역을 늘리는 비용이 아니라, 하드코딩된 단일 구역 가정을 데이터로 빼내는 비용이다. 코드가 이를 뒷받침한다.

| 요소 | 일반화 결과 |
|---|---|
| `ZoneEntry` | 구역 하나를 `zoneName`, `gateBlockade`, `startPoints[]`, `exitPoints[]`, `exitPrefab` 다섯 필드로 기술하는 직렬화 클래스 |
| `CycleManager` | `ZoneEntry[] zones` 배열 하나만 보유. `GetOpenZones()`, `PlaceExits(zone, …)`, `PickStartPoint(zone, …)`로 순회 |
| `BaseDepartureGate` | 열린 구역이 1개면 즉시 출발, 2개 이상이면 `ZoneSelectUI` 호출 |

구역 식별자가 코드에 남아 있지 않다. 따라서 3구역부터는 인스펙터의 `zones` 배열에 원소를 추가하는 작업이다.

다만 n=3 이상은 실증하지 않았으므로 **"6개까지 수용한다"가 아니라 "2구역까지 실증하였고, 일반화 이후 구역 식별자가 코드에 남지 않으므로 이후 구역은 데이터 증축으로 수용된다"** 수준이 방어 가능한 선이다. 4장 표 8의 3.6행에 이미 "부분 완료(검증 완료) / 나머지 구역은 설계 프레임워크만 구축"이라 적었으므로 그 톤과도 맞는다.

### 사례 2 — 특성(퍽) 추가 (대조군)

코드 변경 0줄이다. `Create > Perk`로 `PerkBase` 에셋을 만들고 `MetaProgressManager`의 `allPerks` 배열에 넣으면 선택 화면과 해금 판정에 자동으로 포함된다.

`EvaluateUnlocks()`가 `axis`와 `threshold`를 읽어 판정하고 `GetConditionText()`가 조건 문구를 생성하므로, 특성의 종류가 코드에 존재하지 않는다.

사례 1이 "일반화에 든 비용"이라면 사례 2는 "일반화가 끝난 계층에서의 확장 비용"이다. 두 사례를 대비하면 표 9의 계층 분리가 확장 비용을 어디에 가두는지가 드러난다.

### 사례 3 — 무기 추가 (보조)

`Data/Weapon/`에 `WeaponStatus_Machete`, `_Spear`, `_Axe`, `_Hammer` 네 개의 ScriptableObject가 있고, FSM은 이를 참조할 뿐 수치를 내장하지 않는다. 논문 3.4가 이미 이 구조와 그 한계(애니메이션 클립 재사용 범위로 한정)를 서술하였으므로, 4.3.1에서는 한 문단으로 인용만 해도 된다.

### 4.3.1 구성 제안

세 사례를 "확장에 든 코드 변경량"이라는 하나의 지표로 묶는다.

| 확장 대상 | 신규 파일 | 기존 파일 수정 | 데이터 자산 | 비고 |
|---|---:|---:|---|---|
| 구역 (1→2) | 2 (70줄) | 2 (62줄) | 씬 배치 + `zones` 원소 | 일회성 일반화 |
| 특성 | 0 | 0 | `PerkBase` 에셋 1개 | |
| 무기 | 0 | 0 | `WeaponStatus` 에셋 1개 + 애니메이션 클립 | 클립 재사용 범위 한정 |

## 2. 미구현 — 논문 서술과 어긋나는 것

### 2.1 구역 게이트가 씬에서 연결되지 않았다 (최우선)

`Base&Main1.unity`의 `CycleManager.zones`는 원소 두 개이며, **둘 다 `gateBlockade: {fileID: 0}`으로 비어 있다.**

```
zones:
- zoneName: "1구역"
  gateBlockade: {fileID: 0}
- zoneName: "2구역"
  gateBlockade: {fileID: 0}
```

`ZoneEntry.IsOpen`은 `gateBlockade == null || !gateBlockade.gameObject.activeSelf`이므로, 두 구역 모두 **항상 열린 상태**로 판정된다. 즉 게임을 시작하자마자 출발 게이트에서 2구역을 고를 수 있다.

논문 3.6의 핵심 주장인 "미개방 구역의 SOB는 해당 구역의 보스를 처치해 얻을 수 있는 열쇠로만 해제되며"가 현재 씬에서 성립하지 않는다. 보스를 처치해 열쇠를 얻는 경로 자체는 동작하나(4장 그림 22~24), 그 열쇠가 **구역 개방으로 이어지지 않는다.**

고치는 비용은 작다. 2구역 입구에 `Blockade`를 배치하고 `ZoneEntry[1].gateBlockade`에 할당하면 된다. 코드 수정은 필요 없다.

### 2.2 선택적 블록에이드가 하나도 없다

씬의 `Blockade` 인스턴스는 **1개**이며, 그 메시지는 "탈출구 열쇠 필요" / "탈출"로 최종 탈출구다. "비상구 열쇠 필요" / "기지로 귀환" 두 개는 `Blockade`가 아니라 `BaseReturnExit`다.

논문은 세 곳에서 선택적 블록에이드의 배치를 서술한다.

- 1.2.2 "특정 아이템으로 해제되어 추가 보상을 제공하는 선택적 블록에이드를 배치하고"
- 2.3 "각 구역 내부에는 숨겨진 통로나 보너스 공간, 추가적인 열쇠와 같은 선택적 블록에이드가 배치되어"
- 3.6 "이미 개방된 구역 내부에 남아있는 숨겨진 통로나 추가적인 자원 등 선택적 블록에이드를 공략할 수 있는 경로를 열어두기 위한 것"

`Blockade` 클래스 자체는 선택적/필수적을 구분하지 않으므로, 보너스 공간 입구에 인스턴스를 하나 배치하고 키 아이템만 지정하면 성립한다. 이것도 코드 수정이 필요 없다.

### 2.3 무기·장비 업그레이드가 구현되지 않았다

`Assets/Script/` 전체에서 업그레이드 관련 코드가 **한 건도 검색되지 않는다.**

논문은 네 곳에서 업그레이드를 서술한다.

- 1.2.1 "탐색, 탈출(비상구 및 열쇠), 성장(**제작 및 업그레이드**)으로 순환하는 런 단위 핵심 구조를 구현한다"
- 3.4 "추후 새로운 무기나 **장비 업그레이드 시스템**을 도입할 때" (여기는 향후 과제로 서술되어 문제 없음)
- 3.5 "비상구를 통해 기지로 복귀하여 **장비와 스탯을 강화**하는 과정을 반복한다"
- 3.8 "플레이어는 획득한 상위 자원을 통해 **무기를 업그레이드하고**, 이를 바탕으로 막혀 있던 다음 구역의 블록에이드(보스)를 돌파하는 구조로 연결되도록 설계하였다"

3.4는 향후 과제로 쓰여 있으나 1.2.1과 3.5, 3.8은 구현된 것으로 읽힌다. 3.8의 표 5에도 "상위 무기(돌파) vs 소모품(생존) 자원 배분"이 플레이어 표현력의 근거로 올라가 있는데, 상위 무기 제작이 없으면 이 축의 근거가 사라진다.

선택지는 둘이다. 제작대에서 상위 무기를 만드는 레시피를 데이터로 추가하거나(코드 수정 불필요), 1.2.1·3.5·3.8의 문장을 "제작"만 남기고 업그레이드를 5장 향후 과제로 옮기는 것이다.

### 2.4 구역 수

논문 3.6 마지막이 "총 6개의 구역을 순차적으로 개방하는 최종 구성까지 확장할 수 있다"이고 4장 표 8의 3.6행도 "6개 구역 확장을 위한 모듈형 맵 프레임워크"다. 실제 씬의 `zones`는 2개다. 표 8이 이미 "부분 완료"로 적고 있으므로 3.6 본문의 "확장할 수 있다"를 "확장 가능한 구조를 갖추었으며 현재 2개 구역을 구현하였다" 정도로 맞추면 된다.

### 2.5 더러운 휴지 (코드 118)

어느 루트 테이블에도 없고 제작 레시피도 없어 획득 경로가 없다. 이전 점검에서 지적된 그대로다.

## 5. 처리 순서 제안

1. 2구역 입구에 `Blockade` 배치 후 `ZoneEntry[1].gateBlockade`에 할당 — 씬 작업만, 30분. 3.6의 핵심 주장이 성립하게 된다
2. 선택적 블록에이드 1개 배치 — 씬 작업만
3. 업그레이드: 상위 무기 레시피를 데이터로 추가하거나, 1.2.1·3.5·3.8 문장 수정 중 택일
4. 3.6의 "기존 코드의 수정 없이" → "일회성 일반화 이후 데이터 증축으로" 수정
5. 3.6의 "6개 구역" 서술을 현재 구현(2개)과 맞춤
6. 4.2에 퍽 선택 화면 그림 2장 추가 (그림 22~23, 이후 번호 밀림)
7. 4.3.1 작성 — 위 1절의 세 사례와 표
8. 더러운 휴지를 루트 테이블에 넣거나 삭제
