# 4.3.1 확장성 검증 — 초안

3.1절 그림 8(시스템 구조도)을 축으로 서술한다. 구조도의 데이터 계층에 이미 "로직과 분리된 수치 정의 — 코드 수정 없이 콘텐츠 확장"이라고 명시되어 있으므로, 이 절은 그 문구가 어느 범위까지 성립하는지를 계층 단위로 확인하는 절이 된다.

---

## 본문 초안

### 4.3.1 확장성 검증

 3.1절에서 제시한 그림 8의 계층 구조는 기능을 분리하기 위한 것이었으나, 그 분리는 동시에 콘텐츠를 추가할 때 수정해야 하는 코드의 범위를 결정한다. 본 절에서는 실제로 수행한 확장 작업을 대상으로, 확장이 그림 8의 몇 개 계층에 걸치는지와 그때 발생한 코드 변경량의 관계를 확인한다. 변경량은 형상 관리 기록에서 산출하였다.

 확장 대상별 결과는 표 11과 같다.

| 확장 대상 | 관여 계층 | 신규 파일 | 기존 파일 수정 | 추가 데이터 자산 |
|---|---|---:|---:|---|
| 무기 | 데이터 | 0 | 0 | `WeaponStatus` 1개 |
| 아이템·제작 레시피 | 데이터 | 0 | 0 | `ItemBase` 1개 |
| 컨테이너·몬스터 드롭 구성 | 데이터 | 0 | 0 | `LootTable` 1개 |
| 특성(메타 진행) | 데이터 | 0 | 0 | `PerkBase` 1개 |
| 상호작용 오브젝트 | 월드 오브젝트 | 1 | 0 | — |
| 몬스터·보스 상태 | 상태머신 | 1 | 0 | — |
| 플레이어 상태 | 상태머신 | 1 | 1 | — |
| 구역 | 매니저 · 월드 오브젝트 · UI · 데이터 | 2 | 2 | 씬 배치 |

 표의 위쪽 네 항목은 그림 8의 데이터 계층 안에서 완결된다. 구조도에서 데이터 계층이 상위 계층과 점선, 즉 데이터 참조로만 연결되어 있는 것이 이 결과의 원인이다. 상위 계층은 스크립터블 오브젝트의 형(型)만 알고 그 내용은 알지 못하므로, 같은 형의 자산이 하나 늘어나는 것은 상위 계층에 아무런 변화를 요구하지 않는다. 무기를 예로 들면 전투 상태는 `WeaponStatus`가 어떤 공격력과 사거리를 갖는지 참조할 뿐이므로, 다섯 번째 무기의 추가는 자산 생성만으로 완료된다. 다만 3.4절에서 서술한 바와 같이 이는 애니메이션 클립을 재사용하는 범위에 한정된다.

 특성의 추가도 같은 성질을 갖는다. 특성은 해금 축과 임계값, 적용 효과를 필드로 갖는 스크립터블 오브젝트이며, 해금 판정은 축과 임계값을 읽어 수행되고 조건 문구 또한 같은 필드로부터 생성된다. 따라서 특성의 종류가 코드에 존재하지 않으며, 일곱 번째 특성의 추가는 자산 생성과 목록 등록만으로 완료된다.

 표의 다섯 번째와 여섯 번째 항목은 한 계층 안에서 완결되되 새 파일을 요구한다. 그림 8의 월드 오브젝트 계층은 공통 추상 클래스 `ItObjectBase`를 공유하며, 이 클래스가 하위 클래스에 요구하는 것은 상호작용 가능 여부, 안내 문구, 상호작용 시 동작의 세 가지뿐이다. 나머지 공통 처리는 기반 클래스가 담당하므로 새 오브젝트는 이 세 멤버만 구현하면 기존 코드를 수정하지 않고 편입된다. 상태머신 계층도 동일하다. 몬스터와 보스의 상태는 초기화 시점에 리플렉션으로 수집되므로, 지정된 이름 공간에 새 상태 클래스를 두는 것만으로 상태머신에 등록된다.

 반면 플레이어 상태는 한 파일의 수정을 요구한다. 3.2절에서 서술한 바와 같이 플레이어의 전이는 매 프레임 호출되는 단일 판정 함수에 집중되어 있어, 새 상태가 전이 대상이 되려면 이 함수에 조건을 추가해야 한다. 상태의 수집과 생성은 자동으로 이루어지나 전이 조건만은 그렇지 않다는 점에서, 같은 상태머신 계층 안에서도 플레이어와 몬스터의 확장 비용이 다르다.

 표의 마지막 항목인 구역은 그림 8의 세 계층에 걸친다. 구역의 추가는 사이클 관리자가 어떤 구역을 열린 것으로 판정할지(매니저 계층), 출발 게이트가 어느 시작 지점으로 플레이어를 보낼지(월드 오브젝트 계층), 그리고 열린 구역이 둘 이상일 때 무엇을 보여줄지(UI 계층)를 모두 건드린다. 1구역에서 2구역으로의 확장에서 발생한 변경량은 표 12와 같다.

**[표 12] 구역 확장(1구역 → 2구역)의 코드 변경량**

| 파일 | 계층 | 추가 | 삭제 | 구분 |
|---|---|---:|---:|---|
| `ZoneEntry.cs` | 데이터 | 12 | 0 | 신규 |
| `ZoneSelectUI.cs` | UI | 58 | 0 | 신규 |
| `CycleManager.cs` | 매니저 | 48 | 13 | 수정 |
| `BaseDepartureGate.cs` | 월드 오브젝트 | 14 | 10 | 수정 |
| 합계 | | 132 | 23 | |

주) `git diff main...feature/zoneExpension --numstat -- "*.cs"`의 출력이다.

 기존 파일 두 개에서 발생한 62행의 추가와 23행의 삭제는 구역을 하나 더 만드는 데 든 비용이 아니라, 단일 구역을 전제하던 구현을 일반화하는 데 든 비용이다. 일반화 이전의 사이클 관리자는 시작 지점과 비상구 배치 지점을 자신의 필드로 직접 보유하였으나, 일반화 이후에는 구역을 기술하는 자료형의 배열만을 보유하고 그 배열을 순회한다. 출발 게이트 또한 고정된 시작 지점 대신 인자로 전달받은 구역에서 시작 지점을 얻는다. 그 결과 구역을 식별하는 이름이나 번호가 코드에 남지 않게 되었으며, 이후의 구역 추가는 인스펙터에서 배열에 원소를 추가하고 씬에 지점을 배치하는 작업으로 수행된다.

 다만 본 연구가 실제로 검증한 범위는 두 개 구역까지이다. 세 번째 구역 이후에 코드 변경이 발생하지 않는다는 것은 구조로부터 따라 나오는 추론이며 실측이 아니다. 3.6절에서 상정한 6개 구역 구성까지의 확장은 이 추론 위에 놓여 있고, 이 점은 5장에서 한계로 논의한다.

 정리하면, 그림 8의 계층 분리는 확장 비용을 계층 경계 안에 가두는 방향으로 작동하였다. 데이터 계층에서 완결되는 확장은 코드 변경을 전혀 요구하지 않았고, 단일 계층의 추상 규약을 구현하는 확장은 새 파일 하나만을 요구하였으며, 기존 코드의 수정을 요구한 것은 여러 계층에 걸친 구역 확장과 판정이 한 함수에 집중된 플레이어 상태의 두 경우뿐이었다. 이는 3.1절에서 계층을 분리한 설계 의도가 실행 단계에서 확인된 결과로 볼 수 있다.

## 1장에 넣을 문장 (5장 한계의 복선)

5장에서 "메트로배니아 공간 확장 축은 1~2구역만 구현되어 완전히 가시화되지 않음"을 한계로 쓰려면 1장에 그 범위가 미리 선언되어 있어야 한다. 현재 1장에는 구현 범위에 관한 서술이 없다.

**위치** — 1.2.3 끝, 1.3 시작 전에 한 문단을 추가한다.

**문안**

> 다만 본 연구의 구현 범위는 위 세 목표에 해당하는 시스템 구조를 완성하는 데 있으며, 콘텐츠의 양적 완성은 범위에 포함하지 않는다. 특히 공간 확장 구조는 구역을 데이터 단위로 증축할 수 있는 형태로 설계하되 실제 구현은 두 개 구역까지로 한정하였으며, 이 범위에서 확장 구조가 성립하는지를 4장에서 검증한다. 이로 인한 한계는 5장에서 다시 다룬다.

이 문단은 세 가지를 동시에 한다. 연구 범위를 명시하고, 4.3.1의 존재 이유를 미리 밝히며, 5장 한계의 복선이 된다.

**이미 복선이 있는 한계들** — 다음 네 가지는 3장에서 이미 "5장에서 논의한다"로 넘겨두었으므로 추가 작업이 필요 없다.

| 한계 | 복선 위치 |
|---|---|
| 새 플레이어 상태 추가 시 전이 판정 함수 수정 필요 | 3.2 |
| 고정 순찰 경로의 예측 가능성 미해소 | 3.3 |
| 국소 광원 동시 처리 4개 상한 | 3.9.3, 4.3.2.3 |
| 블록에이드 해제 방식의 다양화 미구현 | 3.6 |

다만 이 넷도 1장에는 언급이 없다. 위 추가 문단의 첫 문장("시스템 구조를 완성하는 데 있으며 콘텐츠의 양적 완성은 범위에 포함하지 않는다")이 이들 전체를 덮는 범위 선언으로 기능하므로, 개별 복선까지 1장에 넣을 필요는 없다.
