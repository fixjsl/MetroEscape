# 4.3.1 증거 수집 목록

## 0. 먼저 — 3구역을 추가하면 논거가 바뀐다

현재 4.3.1의 구역 부분은 "1→2구역에 62행의 기존 코드 수정이 들었고, 3구역 이후는 구조상 0줄일 것"이라는 **추론**으로 끝난다. 3구역을 실제로 추가하고 `.cs` 디프가 비어 있음을 보이면 이것이 **실측**이 된다.

주장의 형태가 이렇게 달라진다.

| | 현재 | 3구역 추가 후 |
|---|---|---|
| 1→2구역 | 기존 2파일 62행 수정 | 동일 (일반화 비용) |
| 2→3구역 | 미실증 — 구조로부터의 추론 | **`.cs` 변경 0** — 실측 |
| 5장 한계 | "6개 구역까지는 추론" | 동일하나 근거가 한 단계 강해짐 |

작업은 씬 작업만이다. `CycleManager.zones` 배열에 원소를 하나 추가하고 시작 지점·비상구 지점을 배치하면 된다.

**같은 브랜치에서 구역 게이트도 함께 연결하기를 권한다.** 현재 `zones[0]`과 `zones[1]` 모두 `gateBlockade`가 비어 있어 2구역이 처음부터 열린다. 3구역 입구와 2구역 입구에 `Blockade`를 배치하고 각 `ZoneEntry.gateBlockade`에 할당하면, 논문 3.6의 "보스 처치로 얻은 열쇠로만 해제된다"는 주장이 씬에서 성립하게 된다. 이것도 코드 수정이 아니므로 `.cs` 디프는 여전히 비어 있다.

## 1. 촬영할 디프 목록

### A. 구역 일반화 (1구역 → 2구역) — 확보 완료

```powershell
git diff main...feature/zoneExpension --numstat -- "*.cs"
git diff main...feature/zoneExpension --diff-filter=A --name-only -- "*.cs"
```

이미 `확장성 검증 깃 스샷/구역확장 코드 일반화 2구역.png`에 있다. 다만 `feature/zoneExpension`이 이미 병합되었다면 나중에 재현이 안 되므로, **부록용으로 커밋 해시를 함께 기록**해 두는 것이 좋다.

```powershell
git log --format="%H %ad %s" --date=short -1 feature/zoneExpension
git merge-base main feature/zoneExpension
```

### B. 구역 추가 (2구역 → 3구역) — **새로 찍을 것, 가장 중요**

3구역 작업을 별도 브랜치에 커밋한 뒤 찍는다.

```powershell
git switch -c feature/zone3
# (유니티에서 3구역 배치 + zones 원소 추가 + gateBlockade 할당)
git add -A
git commit -m "3구역 추가 (데이터·씬만)"

# 핵심 — 스크립트 변경이 없음을 보인다
git diff main...feature/zone3 --stat -- "*.cs"

# 실제로 바뀐 것은 씬과 에셋뿐임을 보인다
git diff main...feature/zone3 --stat
```

첫 번째 명령이 **아무 출력도 내지 않는 것**이 증거다. 스크린샷에는 명령줄과 빈 출력, 그다음 두 번째 명령의 결과가 함께 담겨야 "안 찍은 게 아니라 정말 비어 있다"가 읽힌다.

빈 출력이 허전하면 파일 수를 명시적으로 세는 편이 낫다.

```powershell
git diff main...feature/zone3 --name-only -- "*.cs" | Measure-Object -Line
```

### C. 특성 추가 — 데이터 계층 확장의 대조군

일곱 번째 특성을 하나 만들어 같은 방식으로 찍는다. 에셋 생성과 `MetaProgressManager.allPerks` 등록만 하면 된다.

```powershell
git switch -c feature/perk7
# (Create > Perk 로 에셋 생성 + allPerks 배열에 등록)
git add -A
git commit -m "특성 1종 추가"

git diff main...feature/perk7 --stat -- "*.cs"      # 빈 출력
git diff main...feature/perk7 --stat                # .asset + .unity 만
```

특성 축·임계값·효과가 전부 에셋 필드이므로 `.cs`는 비어야 한다. B와 C를 나란히 놓으면 "계층을 넘지 않는 확장은 코드를 건드리지 않는다"가 두 번 확인된다.

### D. 콘텐츠 식별자가 코드에 없음 — 음성 증거

디프와 별개로, 콘텐츠 이름이 코드에 등장하지 않는다는 것을 직접 보일 수 있다. 짧고 설득력이 있다.

```powershell
git grep -n "구역" -- "*.cs"
git grep -niE "machete|hammer|spear|axe" -- "*.cs"
git grep -n "1구역\|2구역\|3구역" -- "*.cs"
```

출력이 없거나 열거형·애니메이터 이름 정도만 나오면, 구역과 무기의 식별자가 데이터에만 존재한다는 뜻이다. 표 9의 데이터 계층 설명("로직과 분리된 수치 정의")을 직접 뒷받침한다.

### E. 상호작용 오브젝트 추가 — 단일 계층 규약 구현

과거 커밋에서 뽑는다. 새로 만들 필요가 없다.

```powershell
# 파일이 추가된 커밋 찾기
git log --diff-filter=A --format="%h %ad %s" --date=short -- Assets/Script/Object/DIYwaterfilter.cs

# 그 커밋에서 .cs 변경 범위
git show --stat <해시> -- "*.cs"
```

신규 1파일만 나오고 `ItObjectBase.cs`나 다른 기존 파일이 없으면, "새 오브젝트는 추상 멤버 3개만 구현하면 된다"는 3.1의 서술이 실측으로 뒷받침된다.

`DIYwaterfilter` 대신 `StairObject`, `Campfire` 등 어느 것이든 된다. 기존 파일 수정이 섞이지 않은 커밋을 고르면 된다.

### F. 플레이어 상태 추가 — 반례 (표에 꼭 필요)

```powershell
git log --diff-filter=A --format="%h %ad %s" --date=short -- Assets/Script/State/PlayerState/ActiveState/Execution.cs
git show --stat <해시> -- "*.cs"
```

여기서는 `Execution.cs` 신규와 함께 **`PlayerStateMachine.cs` 수정이 나와야 한다.** 3.2절에서 한계로 적은 "새 상태가 전이 대상이 되려면 판정 함수에 조건을 추가해야 한다"가 디프로 확인되는 자리다.

E와 F를 나란히 놓는 것이 4.3.1의 핵심 대비다. 같은 "파일 하나 추가"인데 계층에 따라 기존 코드 수정 여부가 갈린다.

### G. 몬스터 상태 추가 — E의 보강 (선택)

```powershell
git log --diff-filter=A --format="%h %ad %s" --date=short -- Assets/Script/State/MonsterState/ActiveState/Stun.cs
git show --stat <해시> -- "*.cs"
```

리플렉션 수집 덕분에 `MonsterStateMachine.cs` 수정 없이 신규 1파일로 끝났다면 E와 같은 계열의 증거다. 다만 `ChangeStun()` 같은 호출부가 함께 바뀌었을 수 있으니 확인 후 쓸지 정한다.

## 3. 촬영 시 주의

**터미널 폭을 좁혀서 찍는다.** 논문 본문 폭이 17cm이므로 100열 이상이면 줄이 접힌다. 80열 전후가 적당하다.

**명령줄이 보이게 찍는다.** 출력만 있으면 무엇을 실행한 것인지 알 수 없다. 특히 B의 빈 출력은 명령줄이 없으면 증거가 되지 않는다.

**한 그림에 관련 명령 두세 개까지만 담는다.** 기존 스샷처럼 `--numstat`과 `--diff-filter=A`를 묶는 정도가 읽기 좋다.

**작업 전 커밋을 정리한다.** 3구역 브랜치에 관계없는 변경(퍽 `PerkId` 수정, 4장 문서 등)이 섞이면 디프가 지저분해진다. 3구역 작업만 따로 커밋한다.

**`PerkId`를 먼저 고친다.** 현재 퍽 6종의 `PerkId`가 전부 1이다. C의 특성 추가 실험을 하기 전에 1~6으로 정리해야 한다.

## 4. 권장 작업 순서

1. 퍽 `PerkId`를 1~6으로 정리, 해금 기록 초기화
2. `feature/zone3` 브랜치 생성
3. 유니티에서 3구역 배치 — `zones` 원소 추가, 시작 지점·비상구 지점 배치
4. 2구역·3구역 입구에 `Blockade` 배치 후 각 `ZoneEntry.gateBlockade`에 할당
5. 커밋 후 **B** 촬영
6. `feature/perk7` 브랜치에서 특성 1종 추가, 커밋 후 **C** 촬영
7. **D** 촬영 (브랜치 무관)
8. 과거 커밋에서 **E**, **F**, (선택)**G** 촬영
9. 4.3.1 본문 작성 — 표 11(확장 대상별 변경량), 표 12(구역 확장 디프)
10. 3.6과 1.2.2의 "기존 코드의 수정 없이" 문장 수정, 1.2.3 끝에 범위 문단 추가
11. 4.2에 퍽 화면 2장 추가 (그림 22~23, 이후 번호 밀림)

4번까지 하면 논문 3.6의 미구현 지적도 함께 해소된다.
