# 3장 확장성 주장 전수 검증 (2026-09-27)

논문 1~3장에서 "확장", "추가", "수정 없이", "유연하게" 등으로 서술된 주장을 전부 추출하여 실제 코드·씬·에셋과 대조하였다. 총 16건이다.

판정은 네 가지다. **성립** — 코드가 주장대로다. **부분 성립** — 일부만 해당한다. **반증** — 코드가 주장과 다르다. **미실증** — 코드상 가능하나 실제로 해보지 않았다.

## 2. 반증·미실증 항목 상세와 수정 문안

### E1 · E3 · E12 — 구역 추가 (같은 주장의 세 곳)

세 곳 모두 "기존 코드의 수정 없이"를 주장한다. 실제 디프는 다음과 같다.

```
git diff main...feature/zoneExpension --numstat -- "*.cs"
48  13   Assets/Script/Manager/CycleManager.cs
12   0   Assets/Script/Manager/ZoneEntry.cs        (신규)
14  10   Assets/Script/Object/BaseDepartureGate.cs
58   0   Assets/Script/UI/ZoneSelectUI.cs          (신규)
```

기존 파일 두 개가 실제로 수정되었다. **이 디프를 4.3.1의 근거로 제시하면 주장 자체를 반증하는 자료가 된다.**

정확한 사실은 이렇다. 1구역에서 2구역으로 갈 때 든 비용은 구역을 늘리는 비용이 아니라, 하드코딩된 단일 구역 가정을 데이터로 빼내는 **일회성 일반화** 비용이다. 일반화 결과 구역 식별자가 코드에서 사라졌다.

| 요소 | 역할 |
|---|---|
| `ZoneEntry` | 구역 하나를 `zoneName`, `gateBlockade`, `startPoints[]`, `exitPoints[]`, `exitPrefab` 다섯 필드로 기술하는 직렬화 클래스 |
| `CycleManager` | `ZoneEntry[] zones` 배열만 보유. `GetOpenZones()`, `PlaceExits(zone, …)`, `PickStartPoint(zone, …)`로 순회 |
| `BaseDepartureGate` | 열린 구역이 1개면 즉시 출발, 2개 이상이면 `ZoneSelectUI` 호출 |

**수정 문안**

1.2.2 현재:

> 나아가 새로운 구역을 기존 코드의 수정 없이 추가할 수 있는 확장성을 확보하는 것을 목표로 한다.

수정안:

> 나아가 구역을 기술하는 데이터 구조를 코드에서 분리하여, 구역 식별자가 로직에 남지 않는 확장 구조를 확보하는 것을 목표로 한다.

3.1 데이터 계층 현재:

> 이러한 분리는 새로운 무기나 아이템, 나아가 새로운 구역을 추가할 때 로직 수정 없이 데이터 자산의 추가만으로 콘텐츠를 확장할 수 있게 하는 기반이 된다.

수정안 — "구역"을 이 문장에서 빼고 3.6으로 넘긴다:

> 이러한 분리는 새로운 무기나 아이템을 추가할 때 로직 수정 없이 데이터 자산의 추가만으로 콘텐츠를 확장할 수 있게 하는 기반이 된다. 구역 단위의 확장은 데이터 계층뿐 아니라 매니저 계층과 월드 오브젝트 계층에 함께 걸치므로 3.6절에서 별도로 다룬다.

3.6 현재:

> 따라서 동일한 방식의 블록에이드를 사용하는 한 새로운 구역을 추가할 때에는 키 아이템과 보스의 루트 테이블(Loot Table)만 정의하면 되며 기존 코드의 수정이 필요하지 않다. 이러한 구조 위에서 총 6개의 구역을 순차적으로 개방하는 최종 구성까지 확장할 수 있다.

수정안:

> 구역의 구성 정보는 구역명, 진입을 차단하는 블록에이드, 시작 지점군, 비상구 배치 지점군, 비상구 프리팹의 다섯 항목을 갖는 직렬화 자료형으로 분리되어 있으며, 사이클 관리자는 이 자료형의 배열만을 보유한 채 순회한다. 따라서 구역 식별자가 코드에 존재하지 않으며, 구역의 추가는 해당 배열에 원소를 추가하고 키 아이템과 보스의 루트 테이블을 정의하는 작업으로 수행된다. 다만 이러한 구조는 단일 구역을 전제하던 초기 구현을 일반화하는 과정을 거쳐 얻어진 것으로, 그 비용은 4.3.1절에서 정량적으로 제시한다.

### E13 — 6개 구역

현재 씬의 `zones`는 2개다. "확장할 수 있다"는 n=3 이상을 해보지 않은 상태의 단언이다.

수정안 — 위 3.6 문단 뒤에 이어 붙인다:

> 본 연구의 구현 단계에서는 두 개 구역까지 실증하였으며, 최종 구성으로 상정한 6개 구역은 동일한 방식의 데이터 증축으로 수용 가능한 범위이나 실제 구현에는 이르지 못하였다.

4장 표 8의 3.6행이 이미 "부분 완료(검증 완료) / 나머지 구역은 설계 프레임워크만 구축"이므로 톤이 맞는다.

## 4. 표현만 조정하면 되는 것

### IState의 실제 규약은 4개다

논문 3.1과 3.2는 "진입(Enter), 논리 갱신(LogicUpdate), 물리 갱신(PhysicalUpdate), 종료(Exit), 피해 처리(HandleDamage), 진입 가능 여부 판정(CanEnter)"의 여섯을 동일 생애주기로 서술한다. 실제로는 `IState` 인터페이스에 네 개만 있고, `HandleDamage`와 `CanEnter`는 추상 클래스 `State`의 가상 메서드다.

```csharp
public interface IState
{
    public void Enter();
    public void LogicUpdate();
    public void PhysicalUpdate();
    public void Exit();
}
```

"공통 추상 클래스 State와 IState 인터페이스를 공유하여"로 묶어 쓰고 있으므로 틀린 서술은 아니다. 다만 구두시험에서 "IState에 여섯 개가 있느냐"를 물으면 아니라고 답해야 하므로, **"인터페이스가 정의하는 네 개의 생애주기와 추상 클래스가 제공하는 피해 처리·진입 판정"** 정도로 나누어 쓰는 편이 안전하다.

### 리플렉션 수집에 네임스페이스 조건이 있다

상태 수집 코드는 다음과 같다.

```csharp
// PlayerStateMachine
t.IsSubclassOf(typeof(PlayerState)) && !t.IsAbstract

// MonsterStateMachine
t.IsSubclassOf(typeof(MonsterState)) && !t.IsAbstract && t.Namespace == "MonsterStates"

// BossStateMachine
… t.Namespace == "BossStates"
```

몬스터와 보스는 네임스페이스가 일치해야만 수집된다. 즉 새 몬스터 상태를 추가할 때 `MonsterStates` 네임스페이스에 두지 않으면 조용히 누락된다. 3.2의 "동일 규약만으로 확장"에 붙는 실제 제약이므로 4.3.1에서 한 줄 언급할 가치가 있다.

## 5. 3장에 없는데 추가할 만한 확장성 근거

메타 진행은 3장에 설계 절이 없다. 그런데 확장 비용이 가장 낮은 사례다.

특성 추가는 코드 변경 0줄이다. `Create > Perk`로 `PerkBase` 에셋을 만들고 `MetaProgressManager`의 `allPerks` 배열에 넣으면 선택 화면과 해금 판정에 자동으로 포함된다. `EvaluateUnlocks()`가 `axis`와 `threshold`를 읽어 판정하고 `GetConditionText()`가 조건 문구를 생성하므로 특성의 종류가 코드에 존재하지 않는다.

구역 확장이 "일반화에 든 비용"이라면 특성 추가는 "일반화가 끝난 계층에서의 확장 비용"이다. 두 사례를 대비하면 표 9의 계층 분리가 확장 비용을 어디에 가두는지가 드러난다.

**다만 현재 퍽 에셋 6개의 `PerkId`가 전부 1이다.** `IsUnlocked`가 `unlockedPerkIds.Contains(p.PerkId)`이므로 조건 하나만 충족해도 여섯 개가 모두 해금된 것으로 표시된다. 1~6으로 다시 매긴 뒤 해금 기록을 초기화해야 한다.
