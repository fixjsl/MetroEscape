### A-1. [오류] 역운동학을 "적용하지 않았다"고 썼으나 실제로는 적용되어 있다 ★

3.4 마지막 문단:

> 이때 무기의 부착 위치는 **역운동학(IK)을 적용하는 대신** 무기 프리팹에 부착 오프셋을 사전 정의하는 방식을 택하였다. 기존 애니메이션에 IK제약을 적용할 경우 상위 관절의 포즈가 함께 변형되는 문제가 있었기 때문이다.

코드에는 역운동학이 있다. `PlayerStateMachine.OnAnimatorIK`가 왼손의 IK 가중치를 1로 올리고 무기의 보조 그립 지점을 목표로 잡는다.

```csharp
// PlayerStateMachine.cs:603~
void OnAnimatorIK(int layerIndex)
{
    ... animator.SetIKPositionWeight(AvatarIKGoal.LeftHand, 1f);
        animator.SetIKRotationWeight(AvatarIKGoal.LeftHand, 1f);
        animator.SetIKPosition(AvatarIKGoal.LeftHand, currentWeapon.secondaryGrip.position);
        animator.SetIKRotation(AvatarIKGoal.LeftHand, currentWeapon.secondaryGrip.rotation);
    ... else animator.SetIKPositionWeight(AvatarIKGoal.LeftHand, 0f);
}
```

그리고 `Attack.Enter()`가 공격 진입 시 이 가중치를 0으로 내린다.

```csharp
// Attack.cs:27~28
player.animator.SetIKPositionWeight(AvatarIKGoal.LeftHand, 0f);
player.animator.SetIKRotationWeight(AvatarIKGoal.LeftHand, 0f);
```

즉 실제 구조는 "IK를 쓰지 않았다"가 아니라 **오른손은 프리팹 오프셋, 왼손은 IK, 공격 구간에서만 IK 해제**다. 논문이 말하려던 문제(상위 관절 변형)는 이 해제로 회피하고 있다. 수정안:

> 이때 무기를 드는 주손의 부착 위치는 무기 프리팹에 부착 오프셋을 사전 정의하여 처리하고, 양손 파지를 위한 왼손만 역운동학(IK)으로 무기의 보조 그립 지점에 정렬하였다. 다만 공격 애니메이션이 재생되는 구간에서는 역운동학의 가중치를 0으로 내린다. 공격 동작에 IK 제약을 유지하면 상위 관절의 포즈가 함께 변형되기 때문이다.

5.2.1의 대응 문단도 함께 고쳐야 한다. 현재는 "현재는 프리팹 단계에서 오프셋을 수동으로 조정하여 시각적으로 허용 가능한 범위에 맞추고 있으나"로 IK를 쓰지 않는 것처럼 되어 있다. 또 같은 문단의 향후 과제 "부착 오프셋을 무기 데이터에 포함시켜 … 관리할 필요가 있다"는 **이미 `WeaponStatus`에 `holdPosition`·`holdRotation` 필드가 존재하나 코드에서 읽히지 않는 상태**이므로, "필드는 정의되어 있으나 부착 경로가 이를 참조하지 않으므로 연결할 필요가 있다"가 정확하다.

### A-2. [오류] 입력 버퍼는 큐(Queue)가 아니다 ★

3.4:

> 플레이어의 상태 머신(PlayerStateMachine)은 공격, 회피, 패링 등의 입력이 발생했을 때 이를 즉시 폐기하지 않고 일정 시간(bufferTime) 동안 **큐(Queue)에 보관한다.**

표 8의 3.4행도 "**입력 큐(Queue) 기반** 입력 버퍼링 메커니즘"이다. 코드에 `Queue`는 한 번도 등장하지 않는다. 버퍼는 단일 필드다.

```csharp
public StateType bufferinput { get; private set; }   // 열거형 한 칸
public float buffertime { get; private set; } = 0.2f;
public TimeManager bufferTimer = new TimeManager();

public void SetBuffer(StateType buffertag) { bufferinput = buffertag; bufferTimer.Reset(); }
```

`SetBuffer`는 이전 값을 덮어쓰므로 **보관되는 입력은 항상 가장 최근의 한 건**이고, `buffertime`(0.2초)이 지나면 `StateType.None`으로 폐기된다. 수정안:

> 플레이어의 상태 머신은 공격, 회피, 패링, 상호작용 입력이 발생하면 이를 즉시 폐기하지 않고 가장 최근의 한 건을 선입력 슬롯에 보관하며, 보관 시간(bufferTime, 0.2초)이 지나면 폐기한다. 새 입력은 이전 입력을 대체한다.

표 8은 "단일 슬롯 선입력 버퍼(0.2초) 기반 입력 버퍼링"으로 바꾼다. 3.2의 서술("입력은 일정 시간 동안 보관된 뒤 소비되지 않으면 자동으로 폐기된다")은 큐를 언급하지 않아 그대로 두어도 된다.

### A-3. [오류] 상호작용 기반 클래스의 첫 번째 추상 멤버는 "상호작용 가능 여부"가 아니다 ★

3.1과 4.3.1이 같은 표현을 쓴다.

> 이 클래스는 **상호작용 가능 여부**, 화면에 표시할 안내 문구, 상호 작용시 수행할 동작의 세 가지만을 하위클래스가 구현하도록 요구하며

실제 `ItObjectBase`의 추상 멤버 세 개는 `isStuck`, `InteractMessage`, `OnInteractInternal`이다. 그리고 `isStuck`은 **12개 구현체가 모두 `=> false`를 반환하며 프로젝트 어디에서도 읽히지 않는다**(`IInteractable`의 선언과 각 구현체의 override가 전부다). "상호작용 가능 여부"에 해당하는 멤버는 없다.

두 갈래가 있다.

- **서술만 고치기(권장, 저위험).** "상호작용 시 플레이어의 이동을 멈출지 여부"처럼 `isStuck`의 이름에 맞게 쓰거나, 세 멤버를 나열하지 않고 "안내 문구와 상호작용 동작을 포함한 세 멤버"로 둔다.
- **`isStuck`을 인터페이스에서 제거하기.** 미사용 멤버가 사라지고 확장 비용 주장이 오히려 강해지지만("두 멤버만 구현하면 된다"), 3.1과 4.3.1의 "세 가지"·"세 멤버"를 "두 가지"·"두 멤버"로 고쳐야 한다. 4.3.1의 증거 스크린샷(`: ItObjectBase` 검색 결과)은 영향을 받지 않으므로 제거해도 증거는 유효하다.

### A-4. [오류] 표 2의 "공격 속도"는 속도가 아니라 3타 후 대기시간이다 ★

`attackSpeed`는 프로젝트 전체에서 **단 한 곳**에서만 읽힌다.

```csharp
// Attack.cs — 신규 공격 진입 판정
public override bool CanEnter()
{
    if (player.currentWeapon == null) return false;
    if (player.isTired) return false;
```

> 무기별 공격 템포는 3타 콤보를 끝낸 뒤 다음 공격에 진입할 수 있게 되기까지의 대기 시간으로 구현하였으며, 무거운 무기일수록 이 값이 길다.

### A-6. [오류] 셰이더의 탄젠트는 픽셀마다 계산된다

3.9.2:

> **탄젠트 계산은 원뿔의 내각과 외각에 대해 각각 한 번씩만 수행되며**, 픽셀 단위 연산은 나눗셈과 비교로 축소된다.

`tan()`은 프래그먼트 셰이더 본문 안에 있으므로 **픽셀마다** 두 번(내각·외각) 호출된다. `radians()` 변환도 같다.

```hlsl
float pixelTan  = perp / max(along, 1e-5);
float outerTan  = tan(radians(max(_FlashlightOuterAngle, 1.0) * 0.5));
float innerTan  = tan(radians(clamp(_FlashlightInnerAngle, 0.5, _FlashlightOuterAngle - 0.5) * 0.5));
```

논문이 말하려던 요지(역삼각함수 제거)는 유효하므로 문장만 고치면 된다.

> 각 픽셀에서 역삼각함수를 호출해 각도를 구하는 대신, 조준 방향에 대한 전방 성분과 수직 성분의 비율을 내각·외각의 탄젠트와 비교하는 방식을 취하였다. 픽셀 단위 연산이 나눗셈과 비교로 축소된다.

서술을 원래대로 살리고 싶으면 CPU 측(`Flashlight.UpdateShaderGlobals`)에서 `Mathf.Tan`을 계산해 전역으로 넘기면 된다. 코드 두 줄이고, 그러면 "각각 한 번씩만 수행된다"가 문자 그대로 참이 된다.

### A-7. [오류] 코루틴 대기 객체 캐시의 근거가 현재 구현과 맞지 않는다

3.9.5:

> 일정 주기로 동작하는 코루틴에서 반복 사용되는 대기 객체는 간격별로 정적 캐시에 보관하여 재사용한다. 이 캐시를 사용하는 코루틴은 세 곳으로 … **캐시가 없을 경우 각 주기마다 대기 객체가 새로 생성되므로, 특히 매 프레임 동작하는 루틴에서 지속적인 힙 할당이 발생한다.**

캐시를 쓰는 곳이 세 곳이라는 사실은 맞다. 그러나 세 곳의 형태가 다르다.

| 루틴 | 주기 | 대기 객체를 받는 위치 |
|---|---|---|
| `PassiveState.PassiveRoutine` (소음·밝기) | 매 프레임 | **루프 진입 전 1회** |
| `MonsterStateMachine.Detect` (탐지) | 0.1초 | **루프 진입 전 1회** |
| `GameManager.Clock` (게임 내 시간) | 2.5초 | 루프 **안**에서 매 주기 |

앞의 두 곳은 `WaitForSeconds wait = YeildCache.GetIntervals(...)`를 `while` 밖에서 한 번 받아 재사용하므로, **캐시가 없어도 코루틴 시작 시 한 번만 할당된다.** 따라서 "매 프레임 동작하는 루틴에서 지속적인 힙 할당이 발생한다"는 설명은 이 구현에는 해당하지 않는다.

캐시의 실효는 다른 데 있고, 그쪽이 오히려 더 좋은 근거다.

> 대기 객체는 간격별로 정적 캐시에 보관하여 같은 간격을 사용하는 모든 코루틴이 하나의 객체를 공유하도록 하였다. 특히 몬스터의 탐지 판정 루틴은 개체마다 하나씩 동작하므로, 캐시가 없으면 대기 객체가 몬스터 수에 비례하여 존재하게 된다. 한편 게임 내 시간을 진행시키는 루틴은 주기마다 캐시를 조회하는 형태이므로, 이 경우에는 캐시가 주기당 할당을 직접 제거한다.

### A-8. [오류] 5.2.4가 무작위 요소를 잘못 지목했다

5.2.4:

> 몬스터의 소환 위치는 고정이나 **탈출 지점이 무작위로 결정되므로** 측정 시마다 이동 경로가 달라지며

코드에서 무작위인 것은 **시작 지점**이고, 비상구는 그 시작 지점에서 **가장 먼** 지점으로 결정된다.

```csharp
// CycleManager.PickStartPoint — 시작 지점이 무작위
Vector3 raw = zone.startPoints[Random.Range(0, zone.startPoints.Length)].position;

// CycleManager.PlaceExits — 출발한 구역에서는 시작 지점에서 가장 먼 비상구를 고른다
if (z == startzone) { ... foreach (var p in z.exitPoints) { d = Distance(Startpos, p.position); if (d > best) { best = d; chosen = p; } } }
else chosen = z.exitPoints[Random.Range(0, z.exitPoints.Length)];
```

4.3.2.1은 이를 정확히 "시작 지점이 매 런 무작위로 결정되어"라고 썼으므로, 5.2.4만 어긋난다.

> 몬스터의 소환 위치는 고정이나 런의 시작 지점이 무작위로 결정되고 비상구가 그 지점에서 가장 먼 위치에 배치되므로, 측정 시마다 이동 경로가 달라지며

덧붙여 3.1의 "귀환 수단인 비상구가 그 지점으로부터 가장 먼 위치에 배치되므로"는 **출발한 구역에만** 적용되고, 이미 열려 있는 다른 구역의 비상구는 무작위 지점에 배치된다. 한 구절로 한정해 두는 편이 안전하다.

### A-9. [부정확] 상태머신이 개별 상태를 지명하지 않는다는 서술의 범위

3.1과 3.2가 같은 주장을 한다.

> 이로써 새로운 행동을 추가하더라도 상태머신이 상태를 호출하는 로직은 달라지지 않으며, 동일 규약만으로 확장할 수 있는 기반을 마련하였다.

3.3은 여기서 한 걸음 더 나간다.

> 플레이어의 전이는 매 프레임 호출되는 단일 판정 함수에 집중되어 있는 반면, **몬스터의 전이는 각 상태의 고유한 전이 조건에 따라 발생한다.**

그런데 `MonsterStateMachine`도 상태 자료형을 직접 지명한다. 탐지 코루틴과 피격·처형·사망·대상 상실 처리가 모두 상태머신 안에 있다.

```csharp
if (ActiveState is MonsterStates.Idle || ActiveState is MonsterStates.Move || ActiveState is MonsterStates.Return)
    ChangeState<Chase>();
...
if (lostFrames == 0 && ActiveState is MonsterStates.Move) ChangeState<MonsterStates.Idle>();
...
ChangeState<MonsterStates.Hit>();  ChangeState<Battle>();  ChangeState<Return>();
ChangeState<Stun>();  ChangeState<MonsterStates.Idle>();  ChangeState<MonsterStates.Die>();
```

지명되는 상태는 Idle·Move·Return·Chase·Hit·Battle·Stun·Die의 여덟 종으로, 몬스터 상태 9종 가운데 여덟이다. 즉 **상태의 수집과 생성은 리플렉션으로 자동화되었으나, 전이의 연결은 플레이어와 마찬가지로 중앙에 남아 있다.** 이는 4.3.1의 결론("식별자가 코드에 남아 있으면 수정이 발생한다")과 정확히 같은 성질이므로, 정직하게 쓰면 논지가 오히려 강해진다.

- 3.1·3.2: "상태머신이 **상태의 생애주기를 호출하는** 로직은 달라지지 않으며"로 한정한다. 전이 연결은 별개라는 점을 3.2가 이미 밝히고 있으므로 거기에 이어 붙인다.
- 3.3: "몬스터의 전이는 순찰·추적·전투처럼 상태 내부의 조건으로 발생하는 부분과, 탐지 게이지·피격·대상 상실처럼 상태머신이 중앙에서 판정하는 부분으로 나뉜다. 다만 플레이어처럼 모든 전이가 한 함수에 집중되지는 않는다."

## B. 구현되어 있는데 3장에 없는 것

### B-1. [누락] 몬스터는 손전등 원뿔 안에서만 보이며, 이탈 후 10초간 유지된다 ★

3.1은 시야 제한을 렌더 패스의 효과로 귀속한다.

> 본 게임은 지하철을 배경으로 하며 플레이어의 적대적 오브젝트 감지 시야가 손전등의 범위로 제한되는데, 이때 조명은 장면에 배치된 광원 컴포넌트가 아닌 화면 전체를 덮는 단일 패스로 계산된다.

실제로 "몬스터가 보이는가"를 결정하는 것은 렌더 패스가 아니라 몬스터마다 붙은 별도 컴포넌트다.

```csharp
// MonsterFlashlightVisibility.cs — 요지
bool inCone = IsInFlashlightCone();          // CPU에서 원뿔 판정
if (inCone) _revealTimer = 0f;
else if (_wasInCone) _revealTimer = REVEAL_DURATION;   // 이탈 순간 10초 타이머 시작
else _revealTimer = Mathf.Max(0f, _revealTimer - Time.deltaTime);
float target = (inCone || _revealTimer > 0f) ? 1f : 0f;
_currentAlpha = Mathf.MoveTowards(_currentAlpha, target, fadeSpeed * Time.deltaTime);
_mpb.SetColor(ColorID, new Color(1,1,1,_currentAlpha));   // 알파만 덮어쓰기
```

여기서 드러나는 설계 규칙이 셋인데 모두 논문에 없다.

1. 몬스터는 손전등 원뿔 안에 있을 때만 보이고, 손전등이 꺼져 있으면 항상 보이지 않는다.
2. **한 번 비춘 몬스터는 원뿔을 벗어난 뒤에도 10초간 계속 보인다**(`REVEAL_DURATION = 10f`). 플레이어가 위협을 놓치지 않게 하는 완충이며, 게임플레이에 직접 드러난다.
3. 게임플레이 판정용 원뿔은 렌더링 원뿔보다 **의도적으로 넓다**(`outerTan * 1.45f`, `range + 0.04f`). 경계에서 몬스터가 먼저 사라지지 않게 한 여유다.

또한 이 판정은 셰이더와 같은 수식을 **CPU에서 몬스터마다 매 프레임** 수행하며, 손전등 값은 `Shader.GetGlobalVector`로 되읽는다. 이는 3.9의 논지("연산량이 장면의 오브젝트 수가 아닌 화면 해상도에 비례한다")에 대한 단서를 하나 남긴다. 조명 합성은 해상도에 비례하지만 **가시성 판정은 몬스터 수에 비례한다.** 이 대비를 밝히는 것이 4.3.2.1의 결과("부하를 결정하는 요인이 전투 연산이 아니라 기하의 양")와도 잘 맞는다.

3.9에 소절을 하나 추가하거나(예: 3.9.3과 3.9.4 사이에 "3.9.x 게임플레이 가시성의 분리"), 3.1의 해당 문단을 다음처럼 고치고 3.9에서 상술하는 방식이 좋다.

> 화면에 보이는 빛은 사용자 정의 패스가 그리고, 플레이어의 노출 정도를 나타내는 밝기 수치는 별도의 패시브 상태가 손전등의 ON/OFF 플래그로 산출하며, 몬스터가 화면에 드러나는지 여부는 몬스터마다 부착된 별도 컴포넌트가 셰이더와 동일한 원뿔 수식을 CPU에서 계산하여 결정한다. 즉 플레이어가 손전등을 켜는 행위는 위치 노출, 시야 확보, 대상 식별의 세 결과를 낳는다.

표 8의 3.9행에도 "손전등 원뿔 기반 몬스터 가시성(이탈 후 10초 유지)"을 넣는다.

3.9.5가 레이어 캐시를 설명하면서 `Dodge`·`Die` 레이어를 언급하지 않는 것도 여기에 연결된다. 3.4에 한 문장을 넣으면 "고위험-고보상" 논의가 완결된다.

### B-3. [누락] 패링 판정 구간의 피격은 피해가 0이다

`Parry.HandleDamage`는 본문이 비어 있다. 즉 판정 구간 중의 피격은 피해를 전혀 받지 않는다. 반면 `Guard.HandleDamage`는 무기의 가드 배율만큼 감소된 피해를 적용한다.

```csharp
public override void HandleDamage(float Damage) { }                       // Parry
public override void HandleDamage(float Damage)                            // Guard
{ player.status.Hp -= Damage * player.currentWeapon.status.GuardStrength;
  player.status.UseStamina(player.currentWeapon.status.guardStamina); }
```

3.4는 패링 성공의 보상을 "적을 기절 상태에 빠뜨리는" 것으로만 서술한다. **피해 무효화가 보상의 절반**이므로 넣어야 하며, 그래야 "고난도 선택지"와 "실패 시 가드로 완충"의 대비가 성립한다.

### B-4. [누락] 처형 대상은 공격 입력이 처리되는 시점에 선정된다

3.4는 처형의 조건(기절 또는 탐지 게이지 50 이하)만 말하고, 어떻게 발동되는지는 말하지 않는다. 코드에서 처형은 **별도 입력이 아니라 공격 입력의 분기**다.

```csharp

Collider[] stunHits = Physics.OverlapSphere(transform.position, currentWeapon.status.executionRange, 1 << Layercache.Stun);
if (stunHits.Length > 0) execTarget = ...;                      // 기절 대상 우선
if (execTarget == null) { /* Monster 레이어를 훑어 CanBeExecuted() 인 대상 */ }
if (execTarget != null) { execution.setTarget(execTarget); ChangeState<Execution>(); }
else ChangeState<Attack>();
```

한 문장이면 된다.

> 처형은 별도의 입력이 아니라 공격 입력이 소비되는 시점의 분기로 구현하였다. 무기에 정의된 처형 사거리 안에서 기절한 대상을 먼저 찾고, 없으면 탐지 게이지가 50 이하인 대상을 찾아 처형 상태로 진입하며, 둘 다 없으면 일반 공격으로 진입한다.

이때 `executionRange`가 무기별 값(`WeaponStatus`)이므로 표 2에 처형 사거리를 넣거나, 최소한 3.4에서 언급해야 한다. 지금 표 2에는 처형 배율만 있다.

덧붙여 5.2.1이 `Physics.OverlapBox`의 배열 반환을 한계로 지목했는데, 이 처형 판정의 `Physics.OverlapSphere`도 같은 성질이며 **공격 입력마다** 최대 두 번 호출된다. 5.2.1의 해당 문단을 "몬스터의 탐지 판정과 플레이어의 처형 대상 탐색에는 …"으로 확장하는 것이 정확하다.

### B-5. [누락] 사망 시 고유(unique) 아이템은 비율과 무관하게 전량 소실된다

3.5는 "진행에 필수적인 열쇠를 제외한 소지 아이템의 75%를 상실"이라고만 쓴다. 실제 규칙은 세 층이다.

```csharp
// Inventory.LoseOnDeath(rate)
if (item.itemType == ItemType.KeyItem) continue;                 // ① 열쇠 아이템은 면제
if (LootTable.IsUniqueItem(pair.Key)) { uniques.Add(...); }      // ② 고유 항목은 따로 모아
...
int target = Mathf.FloorToInt(total * rate);
foreach (var (item, count) in uniques) RemoveItem(item, count);  //    전량 소실
int remain = Mathf.Clamp(target - uniqueTotal, 0, pool);         // ③ 남은 몫을 수량 가중 추첨
```

그리고 고유 항목은 `LootTable`이 사이클 단위로 관리한다.

```csharp
private static readonly HashSet<int> droppedUniqueItemCodes = new();
public static void ResetUniquesForCycle() => droppedUniqueItemCodes.Clear();   // CycleManager가 호출
```

즉 **고유로 표시된 전리품은 한 사이클에 한 번만 드롭되고, 사이클 리셋 시 드롭 이력이 초기화되며, 사망 시에는 비율과 무관하게 전부 사라진다.** 이것이 3.6의 "공간 확장은 런 단위의 성패에 종속된다"를 실제로 성립시키는 장치이므로 3.5에 두 문장을 넣을 값이 있다.

> 손실 대상은 소지 수량의 합을 기준으로 산정하되, 열쇠로 분류된 아이템은 제외한다. 다만 보스 전리품처럼 고유 항목으로 표시된 아이템은 비율과 무관하게 전량 소실된다. 고유 항목은 한 사이클에 한 번만 드롭되며 그 이력은 사이클 리셋과 함께 초기화되므로, 귀환에 필요한 열쇠는 매 런마다 다시 확보해야 한다.

### B-6. [누락] 보스 AI가 3장에 서술되지 않는다

표 8의 3.3행은 구현 항목으로 "일반 몬스터 FSM 상속 보스 AI (경직 무시, 특수 공격, 구역 트리거)"를 올렸다. 그런데 **3.3 본문에는 보스가 한 번도 등장하지 않는다.** 3.1이 "플레이어, 일반 몬스터, 보스 세 주체"를 언급하고, 3.6이 보스 처치를 열쇠 트리거로 삼고, 4.2의 그림 24가 보스 전투 화면이고, 4.3.2.1이 "보스 전투" 구간을 측정한다. 3장에서 설계를 서술하지 않은 대상이 4장에서 측정 구간으로 등장하는 형태다.

코드에서 확인되는 보스의 성질은 다음과 같고, 3.3 끝에 한 문단으로 정리하면 표 8·4.2·4.3.2와 모두 이어진다.

- `BossStateMachine : MonsterStateMachine`이며 재정의는 11개다. 상태는 9종으로 `BossStates` 이름공간에서 리플렉션으로 수집한다.
- **탐지 게이지를 사용하지 않는다.** `OnEnable`/`OnDisable`을 빈 구현으로 재정의하여 탐지 코루틴을 시작하지 않고, 대신 전투 구역 트리거(`BossStartTrigger`)로 전투가 시작되며 구역 이탈(`BossCombatZone`)로 종료된다.

- 특수 공격은 별도 쿨다운 타이머(`specialTimer`)로 관리된다.

### B-7. [누락] 콤보는 최대 3타다

### B-8. [누락] 진입 가능 판정을 쓰는 상태가 패링만이 아니다

### B-9. ~~3.1의 사이클 리셋 처리 목록~~ — 반영하지 않기로 함

`ExecuteCycleReset()`이 호출하는 것은 여섯이고(플레이어 기지 복귀, 몬스터 리스폰, 컨테이너 복구, 고유 전리품 이력 초기화, 비상구 숨김, 출발 게이트 초기화) 3.1은 그중 셋만 적는다. 그러나 3.1은 계층을 조망하는 절이고 해당 문장도 "일괄 처리한다"로 끝나 열거가 전부라고 주장하지 않으므로, 목록을 늘려도 독자가 얻는 것이 없다. 오히려 비상구 재배치를 여기서 설명하면 바로 다음 문단의 그림 9 서술과 겹친다. **손대지 않는다.**

### B-11. [누락] 표 10과 본문의 "대부분의 클립은 종료 이벤트만"

3.2 본문:

> 회피를 비롯한 **대부분의 클립은 종료 시점에 단일 이벤트만** 가지며

`PlayerAnimationEvent`가 노출하는 애니메이션 이벤트 진입점은 여덟 개다. 표 10에 나온 다섯(`OnAttackCollider`, `OffAttackCollider`, `OncanCombo`, `OnAnimationFinishedAt`, `OnAnimationFinished`) 외에 `OnTurnAnimationFinished`(방향 전환), `OnFootstep`(이동 발소리), `OnEndInvincible`(회피 무적 종료), `OnDamage`(처형 피해 시점)가 있다. 즉 회피 클립에도 종료 이벤트 외에 무적 종료 이벤트가 있고, 이동 클립에는 발소리 이벤트가 있다.

표 10에 회피(`OnEndInvincible`)·처형(`OnDamage`)·이동(`OnFootstep`) 행을 더하거나, 본문을 "공격 클립을 제외한 단발 동작 클립은 종료 이벤트를 중심으로 구성되며"로 완화한다. B-2의 회피 무적을 본문에 넣는다면 표 10에 회피 행을 추가하는 쪽이 자연스럽다.

### B-12. [누락] 국소 광원은 색도 함께 전달된다

3.9.3:

> 매니저는 … 등록된 광원의 월드 좌표를 뷰포트 좌표로 변환한 뒤 **위치·범위·강도**를 하나의 4차원 벡터로 묶어 전역 셰이더 배열에 전달한다.

코드는 두 배열을 쓴다.

```csharp
lightData[i]   = new Vector4(vp.x, vp.y, l.Range, l.Intensity);
lightColors[i] = l.LightColor;
Shader.SetGlobalVectorArray("_PointLightData", lightData);
Shader.SetGlobalVectorArray("_PointLightColor", lightColors);
```

"위치·범위·강도를 하나의 4차원 벡터로 묶고, 색을 별도의 배열로 함께 전달한다"로 고친다. 셰이더도 `_PointLightColor[li].rgb`를 곱하므로 색은 실제로 쓰인다.

### B-13. [누락] 조명 합성의 최종 식

3.9.1은 "이 스냅샷을 입력으로 받아 조명을 합성한다"에서 멈춘다. 셰이더의 마지막 두 줄이 그림 29의 화면을 사실상 결정한다.

```hlsl
float3 litColor = col.rgb * BEAM_DIM + flashContrib + pointContrib;   // BEAM_DIM = 0.05
return lerp(col * DARK_FACTOR, float4(litColor, col.a), totalMask);   // DARK_FACTOR = 0.02
```

즉 빛이 닿지 않는 영역은 원본 색의 2%, 빛이 닿는 영역은 원본 색의 5%에 조명 기여를 더한 값이며, 두 결과를 마스크로 보간한다. 4.2의 그림 29 설명("빛이 닿는 영역 내의 사물만 식별이 가능하며, 그 외의 공간은 짙은 어둠에 잠겨 있어")이 이 식의 결과이므로, 3.9.1에 한 문장을 넣으면 4.2가 근거를 갖는다.

## C. 표 2를 다시 짜야 한다

A-4와 B-4에서 나온 문제를 한데 모으면 표 2는 세 가지가 함께 어긋난다.

**단위가 없다.** 공격력(수치), 3타 후 대기시간(초), 사거리(m), 경직도(초), 공격 시 소모 스태미나(수치), 처형 배율(배), 가드 피해 배율(배)이 모두 숫자만 적혀 있다. 열 머리에 단위를 붙여야 한다.

**"경직도"의 의미가 본문에 없다.** 코드에서 이 값은 `WeaponStatus.stunStrength`이고, `MonsterStateMachine.OnHit(Damage, stunStrength)`가 이를 피격 상태의 지속 시간으로 넘긴다(`hitState.SetHitduration(stunStrength)`). 즉 **피격 시 몬스터가 경직에 머무는 시간(초)**이다. 그런데 3.4는 "경직"을 한 번도 설명하지 않고 "기절(Stun)"만 다루며, 몬스터의 기절 시간은 무기가 아니라 몬스터의 `status.stunTime`으로 정해진다. 독자가 경직도와 기절을 같은 것으로 읽게 되어 있다. 표 2 아래에 한 줄이면 해결된다.

> 주) 경직도는 피격 시 몬스터가 경직 상태에 머무는 시간(초)이며, 패링 성공으로 발생하는 기절의 지속 시간은 몬스터별 값으로 별도 정의된다.

**본문의 주장에 필요한 열이 빠져 있다.** 3.4는 "가드와 패링 역시 스태미나를 소모하므로"라고 쓰는데, 그 값은 무기별(`guardStamina`, `parryStamina`)인데 표에는 공격 스태미나만 있다. 처형 사거리(`executionRange`)도 무기별인데 없다. 최소한 각주로 "가드·패링 소모 스태미나와 처형 사거리 또한 무기별로 정의되어 있으며 표에서는 생략하였다"를 넣거나, 열을 추가한다.

참고로 `WeaponStatus`에는 표 2에 없는 `bloodStrenth`(출혈 강도)도 있다. 출혈은 논문 어디에도 없으므로, 실제로 동작한다면 3.4에 한 줄이 필요하고 사용하지 않는 필드라면 그대로 두어도 무해하다.

## D. 구현 결함 — 5.2.1에 넣거나 고칠 것

### D-1. 제작 실패 시 재료만 소실될 수 있다

3.8 마지막 문단은 크래프팅의 트랜잭션 성격을 명시적으로 주장한다.

> 재료의 차감과 산출물 생성이 사전에 가능한지 판별하여 **재료가 충분할 때만** 산출물을 생성한다.

재료 쪽은 맞다. 그러나 산출물을 넣지 못하는 경우가 처리되지 않는다.

```csharp
// ItemBase.Craft
public void Craft(Inventory inventory)
{
    if (!CanCraft(inventory)) return;                                  // 재료 검사만
    foreach (var material in materials) inventory.RemoveItem(material.item, material.amount);
    inventory.AddItem(this);                                           // ← 무게·슬롯 초과면 false
}
```

`AddItem`은 `currentWeight + addWeight > curMaxCarryWeight`이거나 슬롯이 꽉 차면 `false`를 반환한다. `CraftingUI`도 `CanCraft`만 보고 버튼을 활성화하므로(`UpdateCraftButton`), **무게 한계에 걸리면 재료는 사라지고 결과물은 생기지 않는다.** 허기 페널티로 최대 소지 무게가 40%로 줄어든 직후가 정확히 그 상황이고, 이는 3.8이 "크래프팅 결과의 불확실성이 자원 상실이라는 불합리한 좌절감으로 이어지는 것을 방지하기 위한 설계"라고 쓴 의도와 반대다.

고치는 쪽이 논문에 유리하다. `AddItem`의 반환값을 보고 실패 시 재료를 되돌리거나, `CanCraft`에 산출물의 무게·슬롯 여유 검사를 더하면 된다. 고치지 않는다면 5.2.1에 한 문단으로 남긴다.

### D-2. 렌더 패스의 "사전 할당 배열" 서술

3.9.5의 "광원 데이터 전달에 사용되는 배열은 고정 크기로 사전 할당하여 재사용하였으며"는 `ScreenPointLightManager`에서는 정확히 성립한다(`readonly Vector4[4]` 두 개를 재사용).

다만 `FlashlightRendererFeature`는 사정이 다르다. 사전 할당해 둔 `_plDataBuf`·`_plColorBuf`가 **선언만 되어 있고 쓰이지 않으며**, 실제 경로는 매 프레임 `Shader.GetGlobalVectorArray`를 호출한다. 이 API는 호출마다 새 배열을 반환하므로, 렌더 그래프 기록 단계에서 프레임당 두 개의 배열이 할당된다.

```csharp
private static readonly Vector4[] _plDataBuf  = new Vector4[4];   // 미사용
private static readonly Vector4[] _plColorBuf = new Vector4[4];   // 미사용
...
var srcData  = Shader.GetGlobalVectorArray("_PointLightData");    // 프레임당 새 배열
var srcColor = Shader.GetGlobalVectorArray("_PointLightColor");
```

4.3.2.2가 측정한 프레임당 GC 할당 0 B와 모순되지는 않는다. 측정 대상은 렌더 스레드의 `FlashlightPass` 마커와 메인 스레드의 `ScreenPointLightManager.LateUpdate` 마커이고, 이 할당은 렌더 그래프 기록 단계에서 발생하므로 두 마커 밖이다. 그래도 서술은 조정하는 편이 안전하다.

- 3.9.5: "광원 데이터 전달에 사용되는 배열은 광원 관리자에서 고정 크기로 사전 할당하여 재사용하였으며"로 주체를 밝힌다.
- 4.3.2.2의 결과 문단에 "이 값은 측정한 두 구간에 대한 것이다"를 이미 각주로 밝히고 있으므로 추가 수정은 불필요하다.
- 미사용 정적 배열 두 개를 활용해 `GetGlobalVectorArray` 호출을 제거하면 서술이 그대로 참이 된다. 세 줄이면 된다.

## E. 확인이 필요한 것

### E-1. [확인] 플레이어에 실제 `Light` 컴포넌트가 붙어 있다 ★

3.9는 "유니티의 광원 컴포넌트를 장면에 배치하는 일반적인 방식 대신"을 전제로 논지를 세우고, 3.1도 "장면에 배치된 광원 컴포넌트가 아닌"이라고 쓴다. 그런데 코드는 플레이어 자식 계층에서 `Light`를 찾아 보관하고, 손전등 토글이 그 컴포넌트의 `enabled`를 직접 바꾼다.

```csharp
currentLight = GetComponentInChildren<Light>();   // PlayerStateMachine.Awake
...
bool next = currentLight == null || !currentLight.enabled;
if (currentLight != null) currentLight.enabled = next;
IsLightOn = next;
```

이 `Light`의 강도가 0에 가깝다면 켜짐/꺼짐 상태를 담는 표식일 뿐이므로 논문의 서술은 유지되지만, 그래도 "광원 컴포넌트는 ON/OFF 상태를 보관하는 용도로만 두었으며 조명 표현에는 기여하지 않는다" 한 줄이 필요하다. 반대로 강도가 실제로 들어가 있어 장면을 비추고 있다면 3.9의 전제를 손봐야 한다.

**인스펙터에서 플레이어 자식의 Light 컴포넌트 Intensity를 확인해 주세요.** 상태 표식으로만 쓰는 것이라면 `bool` 하나로 바꾸는 편이 서술과 구현이 모두 깔끔해진다(`NoiseABright`도 이 `Light`를 필드로 받아 두었지만 사용하지 않는다).

### E-2. [확인] 전투 시작 전의 보스는 처형 조건을 만족한다

처형 대상 판정은 `CanBeExecuted() => status.detection_gauge <= 50f`이고, 보스는 리셋 시 `detection_gauge = 0f`로 두었다가 플레이어가 전투 구역에 진입하면 `100f`로 올린다. 따라서 **트리거 진입 전의 보스는 게이지가 0이므로 처형 사거리 안에 들어가면 처형 대상이 된다.** 의도된 설계(선공 보상)라면 3.4에 한 줄을 넣을 값이 있고, 의도가 아니라면 보스의 초기 게이지를 100으로 두거나 `CanBeExecuted`를 재정의해야 한다.

### E-3. [확인] 표 4의 감소율과 코드 값의 대응

앞선 검토(D-2)에서 지적한 단위 문제의 근거를 확인하였다. 코드의 기본값은 **게임 내 1분당** 허기 `0.1`, 갈증 `0.3`이며(`PlayerStatus.hungerDecreasePerMinute`, `waterDecreasePerMinute`), `HungerThirst`가 게임 내 1분 이벤트마다 누적한 뒤 정수부만 차감한다. 게임 내 1분이 실시간 2.5초이므로 실시간 1분에는 24배가 적용되어 허기 2.4, 갈증 7.2가 되고, 표 4의 값과 본문의 9.7분·29.2분은 **실시간 기준으로 정확하다.**

다만 인스펙터에서 이 두 값을 덮어썼을 수 있으므로, 플레이어의 Survival 항목이 `0.1`/`0.3`인지 한 번 확인해 두면 좋다. 표 4의 열 머리를 "실시간 분당 감소율"로 바꾸고 각주에 게임 내 1분당 값을 병기하라는 제안은 그대로 유효하다.

## F. 서술은 정확했던 것

대조 결과 아래는 코드와 한 글자 단위로 맞았다. 심사에서 물어도 그대로 답할 수 있다.

**3.2 전이 판정의 우선순위.** 본문과 그림 10이 제시한 순서 — 이동 잠금 → 캔슬 구간의 회피·패링 → 콤보 구간 → `canChanged` 확인 → 웅크리기 진입 → 패링 중 방어 유지 → 선입력 버퍼 → 방어 입력 해제 → 웅크리기 유지 → 이동 입력 → 대기 복귀 — 가 `CheckStateChange()`의 분기 순서와 **정확히 일치**한다.

**3.2 리플렉션 수집.** "PlayerState의 모든 구체 하위 클래스를 수집하여 한 차례만 생성", 자료형을 키로 하는 딕셔너리 보관, 이후 전이는 기존 인스턴스 재사용 — 모두 그대로다.

**3.2 히스테리시스.** "최대 스태미나(감소 적용 전 원본 값)의 30%까지 회복되어야 해제"가 `status.MaxStamina * 0.3f`(`curMaxStamina`가 아니라 `MaxStamina`)와 일치한다. 이 괄호 한 개가 정확해서 서술이 검증된다.

**3.2 콤보 윈도우 조건.** "콤보 단계가 2 미만인 경우에만 콤보 구간을 함께 여는데, 이것이 콤보 1타와 2타에만 추가 입력 유예가 적용되는 이유"가 `OpenAttackCancelWindow(withCombo: ComboIndex < 2)`와 일치한다.

**3.2 공격 종료 이벤트의 인덱스 전달.** "공격 상태에 인자를 받지 않는 기본 종료처리를 차단하고 이 이벤트만 수용하게 한다"가 `Attack.OnAnimationFinished`의 경고 후 차단 + `OnAnimationFinishedAt(int)`의 인덱스 비교와 일치한다.

**3.3 표 1의 인지도 산출식 전체.** 소음은 차폐 시 0.2배 감쇠 후 거리로 나눔, 빛은 차폐 시 0, 거리 1 미만은 1로 계산 — `Mathf.Max(dist, 1f)`까지 정확하다.

**3.3 게이지 누적·감쇠·전이 조건.** 민감도를 곱해 초당 증가량으로 누적(`awareness * detectionSpeed * 0.1f`), 진정도만큼 감소(`recovery * 0.1f`), 100 도달 시 대기·이동·복귀 상태에서만 추적 전이, 손전등을 켠 채 전투 범위 진입 시 즉시 100, 탐지 범위 이탈 2초 후 대상 상실 및 복귀 — 전부 일치한다(2초는 0.1초 × 20회).

**3.3 처형 관련 판정.** 게이지 50 이하가 처형 대상(`<= 50f`), 처형 실패 시 기절 여부와 무관하게 전투 상태 전환(`OnExeHit` → `ChangeState<Battle>()`), 기절에서 빠져나오며 게이지 100 설정(`Stun.Exit()`에서 `detection_gauge = 100f`) — 세 문장 모두 정확하다.

**3.1 상호작용 기반 클래스의 공통 처리.** 트리거 진입 시 등록과 안내 문구 출력, 이탈 시 해제, 중복 입력 방지(`isInteracting`), 재사용 대기 시간(`interactCooldown`), 최초·반복 상호작용의 효과음 구분(`PlayInteractSound`), 여러 대상 중 최근접 우선(`OrderBy(...).First()`) — 여섯 가지가 모두 기반 클래스에 있다.

**3.1 런의 성공과 실패가 같은 리셋 경로를 공유한다는 서술.** 비상구 상호작용(`BaseReturnExit.OnInteractInternal`)과 사망 후 재시작(`Die.RespawnRoutine`)이 **둘 다 `CycleManager.ExecuteCycleReset()`을 호출**한다. 논문의 핵심 주장 하나가 코드로 그대로 확인된다.

**3.5 실패 처리의 2단계.** `inventory.LoseOnDeath(...)` → `Chance--` → `Chance > 0`이면 재시작, 아니면 `GameManager.GameOver()`. 목숨 기본값도 `Chance = 3`이다.

**3.6 블록에이드의 단순화된 SID.** 열쇠 미보유 시 안내 문구만 갱신, 보유 상태에서 상호작용하면 열쇠를 소모하고 비활성화, 해제 동작은 가상 메서드(`protected virtual BlockadeInteract()`)로 분리 — 그리고 `ExecuteCycleReset`이 블록에이드를 복구하지 않으므로 "개방된 경로는 해당 세션 동안 소실되지 않는다"가 성립한다.

**3.6 구역 자료형과 개방 판정.** `ZoneEntry`가 구역명·차단 블록에이드·시작 지점군·비상구 지점군·비상구 프리팹의 다섯 항목을 갖고(4.3.1의 서술과 일치), `IsOpen`이 블록에이드의 활성 여부로 결정된다. 출발 게이트가 "열린 구역이 둘 이상인 경우에만 선택 화면을 호출"하는 것도 `if (open.Count == 1) Confirm(...) else ZoneSelectUI...`로 그대로다.

**3.7 페널티의 즉시 적용.** 허기·갈증의 setter 안에서 임계값 30을 검사해 `curMaxCarryWeight`·`curMaxStamina`를 바꾸고, `AddItem`이 `curMaxCarryWeight`를 참조하므로 "플레이어의 목적에 직접적인 제약"이 실제로 작동한다.

**3.8 크래프팅의 데이터 구조.** `ItemBase` 안의 `CraftMaterial` 구조체 목록, `CanCraft`의 종류·수량 검사, 확률 개입 없는 확정적 결과 — 표 5의 서술과 일치한다(D-1의 예외만 별개다).

**3.9.1 렌더 패스의 구성.** 투명 오브젝트 이후 삽입(`RenderPassEvent.AfterRenderingTransparents`), 깊이 버퍼 없는 텍스처로 스냅샷 복사(`desc.depthBufferBits = 0`), 메시 자산 없이 삼각형 하나(`DrawProcedural(..., MeshTopology.Triangles, 3)`) — 세 가지 모두 정확하다.

**3.9.3 광원 상한의 근거.** "셰이더의 배열은 고정 크기로 선언되어야 하고 전역 벡터 배열의 크기 또한 최초 설정 시점에 확정되므로"가 셰이더의 `float4 _PointLightData[4]`와 `Awake`에서 한 번 크기를 확정하는 구조로 뒷받침된다. 매 프레임 말미(`LateUpdate`) 갱신도 정확하다.

**3.9.4 두 가지 연산 축소.** 상하 경계 밖 픽셀의 조기 반환이 원뿔 판정과 광원 반복 **앞에** 있고(`if (playMask < 0.001) return col * DARK_FACTOR;`), 반복문이 `_PointLightCount`만큼만 돈다. 둘 다 코드 위치까지 서술대로다.

**3.9.2 거리 감쇠.** "사거리 대비 거리의 비율을 1에서 뺀 값을 제곱"이 `falloff = 1 - saturate(d/range); falloff *= falloff;`와 일치하고, 각도 경계와 사거리 끝단에 각각 별도의 그라데이션 폭(`ANG_FADE`, `ARC_FADE`/`EDGE_BLUR`)이 있다. 바닥·천장 Y 좌표와 하이라이트 두께를 4차원 벡터에 함께 담아 전달하는 것도 `_FloorCeilingY`로 그대로다.

**3.9.5 나머지 세 항목.** 프로퍼티 식별자의 정적 정수 캐싱(`static readonly int` 13개), 정적 람다로 클로저 생성 억제(`builder.SetRenderFunc(static (...) => ...)`), 레이어 인덱스의 정적 캐시(`Layercache` 7개) — 모두 서술대로다.

**5.2.3의 세 가지 렌더링 한계.** 광원 상한 4개, 비상구 표지등이 한 슬롯 상시 점유, 등록 순서로 선택하며 절두체 컬링 없음(`Mathf.Min(lights.Count, MaxLights)`와 앞에서부터의 순회), 카메라마다 패스 실행(`AddRenderPasses`에 카메라 필터 없음) — 네 가지 모두 코드로 확인된다.

## G. 표 9의 스크립트 수는 전부 맞았다

현재 `Assets/Script` 전체를 세어 표 9와 대조한 결과다.

| 설계 계층 | 구현 위치 | 실제 `.cs` 수 | 표 9 |
|---|---|---:|---:|
| 데이터 | Item 8 + Status 3 + Perks 1 | 12 | 12 |
| 상태머신 | State 43 + Interface 3 + PlayerEquipment 5 + MonsterAttack 1 | 52 | 52 |
| 매니저 | Manager 14 + Input 1 | 15 | 15 |
| 월드 오브젝트 | Object | 13 | 13 |
| UI | UI 22 + StartMenu 2 + Tutorial 2 | 26 | 26 |
| 렌더링 | Rendering 3 + Camera 1 | 4 | 4 |
| **합계** | | **122** | **122** |

제외 항목도 맞는다. `Script/Editor` 4개 + `Assets/Editor/MetaProgressEditor.cs` 1개 = 에디터 전용 5종, `Script/Measurement/PerfLogger.cs` 1개 = 측정 도구 1종이며, 122 + 5 + 1 = **128**로 각주의 전체 `.cs` 파일 수와 일치한다.

다만 앞선 검토에서 지적한 표 9의 문구 세 곳은 여전히 손봐야 한다.

- 월드 오브젝트의 "ItObjectBase 및 **상호작용 오브젝트 12종**" → 13개 파일의 구성은 `ItObjectBase` 1 + 파생 10 + 비파생 보조 2(`StairObject`, `ItemPlacementController`)다. 4.3.1이 말한 11번째 파생 클래스는 `UI/Tutorial/WeaponPickup.cs`로 UI 계층에 집계되어 있다.
- 상태머신의 "**플레이어(11+3)**" → 액티브 11종은 정확하고, 뒤의 3은 패시브 파일 3개(허기·갈증, 소음·밝기, 그리고 추상 기반 클래스)다. 실제 인스턴스는 패시브 2개이므로 "액티브 11종·패시브 2종과 공통 기반"이 오해가 없다.
- 렌더링의 구현 위치 "Script/Rendering, Camera, **Assets/Shader**" → 셰이더 4종 가운데 `UIAlwaysTop.shader` 하나는 `Script/Shader`에 있다. 위치를 둘 다 적거나 파일을 옮긴다.
